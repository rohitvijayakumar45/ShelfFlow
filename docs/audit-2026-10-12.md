# Requirements audit — 12 October 2026

Scope: the whole repository at commit `1d0e93c` plus the fixes listed below, checked against the
original ShelfFlow specification (sections 1–14). Hardware context: one ESP32-S camera board with
OV3660, one ordinary ESP32 used as the programmer instead of a USB-TTL adapter, and one RC522.

Legend: **PASS** = implemented and exercised by automated tests or builds in this audit.
**PARTIAL** = implemented, but a stated part is missing or only simulated. **OPEN** = requires physical
hardware or data that does not exist yet. Nothing here is physically verified.

## Defects found and fixed

| # | Severity | Finding | Fix | Verification |
|---|---|---|---|---|
| F1 | High | Sensor firmware publishes HEALTH live every 500 ms, each consuming a sequence number, while BARRIER/WEIGHT/RFID drain later from the flash queue. Backend treated any lower sequence as late, so a sensor **flush barrier could never be acknowledged** and exit reconciliation always looked incomplete. | `backend/service.py`: HEALTH no longer advances or is judged against the per-boot ordering watermark; durable events still are. | New tests `test_best_effort_health_does_not_make_queued_barrier_late` (failed before fix, passes after) and `test_durable_event_ordering_still_rejects_older_barrier` |
| F2 | Medium | Device flash queue sent the first file in LittleFS name order — lexicographic, so `…-10.json` went before `…-9.json`, producing avoidable out-of-order events. | `firmware/common/Device.h` now sends the lowest queued sequence first. | Shelf + gate builds |
| F3 | Medium | `vision/run.py` Mode B called `/mode?high=0` on **every loop iteration** while idle (doubling camera HTTP load) and an HTTP error from a resolution switch outside the per-frame `try` would terminate the vision process. | Switch only on state change; failures are recorded on the active collection and never fatal. | Import check, full test suite |
| F4 | Medium | No usable procedure for flashing the camera through the spare ESP32: no download-mode confirmation, no power guidance, no protection against esptool silently writing camera firmware **into the programmer**, no way to identify the carrier. | Rewrote [programming-camera.md](programming-camera.md) (two methods, wire tables, meter checks, loopback tests, MAC safety check). Added `esp32cam-identify` (chip/flash/PSRAM/MAC, no camera pins) and `esp32cam-pinmap-probe` (accepts the AI-Thinker candidate map only after reading OV3660 PID 0x3660 **and** a JPEG). | Builds + upload command inspection |
| F5 | Low | Camera server never reported its IP address, so the user could not find `CAMERA_URL`. | Prints `WIFI_CONNECTED ip=… rssi=… ov3660=ok|FAILED` and `WIFI_LOST`. | Build |
| F6 | Low | Shelf controller produced no local output, so RC522 / HX711 could not be brought up without the full backend + broker. | 1 Hz `DIAG raw tray-a=… tray-b=… rc522_version=0x.. wifi mqtt fs` line and `DIAG RFID uid=…`. New [sensor-controller-bringup.md](sensor-controller-bringup.md). | Build |
| F7 | Low | Opening a serial monitor could reset the programmer (DevKit auto-reset), breaking Method B mid-session. | `monitor_dtr = 0`, `monitor_rts = 0` in programmer and camera PlatformIO environments. | Build |

## Open findings (not fixed — need a decision or hardware)

| # | Finding | Recommendation |
|---|---|---|
| O1 | **Hardware inventory gap.** The design needs a 2nd ESP32 (gate controller) and a 2nd RC522 (gate UID read) in addition to the items reported; also 2× HX711, 2× four-wire load cells, servo, release beam, position switch, and a 5 V ≥ 2 A camera supply. | Buy before gate demo. Until then the gate runs in simulation / audited manual assignment (already implemented). |
| O2 | Sensor HEALTH events (2 trays × 2 Hz) are each stored as `sensor_events` rows with an outbox ACK — about 345 k rows/day, never pruned. | Lower firmware HEALTH rate (e.g. 5 s) or add a retention job for HEALTH rows. Not changed: affects the device-health UI cadence. |
| O3 | Firmware clock is NTP whole seconds, `clock_synced=false`, 1000 ms uncertainty, so physical fusion always vetoes `CLOCK_UNCERTAINTY`. | Implement camera/sensor offset calibration (documented as remaining work). Physical mode stays review-first. |
| O4 | No explicit task watchdog configuration in firmware (loops are non-blocking and yield, i.e. watchdog-*compatible*, but a hung SPI/HTTP call is not reset). | Add `esp_task_wdt` subscription to `loop()` after physical timing is measured. |
| O5 | Optional status LED on GPIO27 is in the BOM/pin map but not driven by firmware. | Cosmetic; implement when hardware exists. |
| O6 | Camera transport is authenticated JPEG polling; no MJPEG stream on the camera firmware. | Spec says "MJPEG where supported" — acceptable; dataset `mjpeg` tool targets an external endpoint. |
| O7 | MQTT is cleartext with the device key inside the payload; firmware TLS not implemented. | Prototype LAN only (documented in security.md). |
| O8 | Camera carrier pin map is still unconfirmed. | Run `esp32cam-pinmap-probe`; only `PROBE_PASS pid=0x3660` permits creating `board_config.h`. |
